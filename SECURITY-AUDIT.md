Scope: repository at `757e775` plus this branch's uncommitted changes, the current Supabase project's read-only schema/policy metadata and advisors, and isolated migration tests. No production credentials or user records were read, and the new migration has **not** been applied to production.

## Control-by-control review

- **Authentication:** Email/password confirmation, Google and gated Apple use the existing Supabase SSR client and fixed canonical `/auth/callback` PKCE flow. `startSocialSignIn` allowlists providers, checks the flag, canonicalizes the origin, and rejects non-Supabase authorization URLs. Callback bounds the code, exchanges it server-side, verifies `getUser()`, and redirects to a fixed `/profile`; caller-supplied destinations are not reflected. `safeNext` restricts password-login `next` to local paths. Logout clears SMS state and signs out locally. The profile trigger creates once and does not use provider metadata for roles or overwrite an existing profile. Apple relay email may create a separate identity if Supabase does not auto-link it; never force-link on unverified metadata. Tests cover these cases at the application boundary, **not** live Apple/Google provider configuration. Supabase Auth owns password hashing, cookies and rate controls; leaked-password protection is currently disabled in the project advisor and requires an owner decision/configuration.
- **Authorization / API / actions:** `src/lib/auth.ts` uses verified `auth.getUser()` for viewer and action contexts; admin actions request `actionContext(true)`. The single PDF access API checks authenticated user, published logical book and published edition association before a 60-second signed URL. Reading, messages, support, homework, SMS and AI actions use owner/admin context, typed input bounds and owner-aware RLS/RPCs. The repo has many SECURITY DEFINER RPCs; sampled core functions have explicit `auth.uid()`, ownership or admin checks and pinned search paths. The live advisor reports 74 authenticated-callable SECURITY DEFINER functions; this is a privileged boundary requiring continued function-by-function review after future migrations, not evidence by itself of an exploitable issue.
- **Supabase:** Read-only live inventory found 42 `public` tables, all with RLS enabled. `friend_request_events` has RLS with no direct policy and revoked direct grants: intentional trigger-only access. Broad authenticated SELECT policies apply to shared school data (`classes`, `subjects`, schedules/calendar), not user-private rows. Existing `book-files` bucket is private with publication/reader policies; avatar paths remain owner-scoped and cooldown-protected. The new cover policy does not change PDF or avatar rules. The advisor also flagged multiple permissive policies where admin/read paths overlap; these are intentional alternatives, but should be rechecked on policy changes. The added `NOT VALID` constraint checks **new/updated** rows immediately; pre-existing rows need separate validation before `VALIDATE CONSTRAINT` is considered. No production SQL write was made.
- **Secrets/privacy:** Only public Supabase URL/publishable key are client configuration. Repository scans for `.env` tracking, `service_role`, private keys, OAuth secrets and token literals did not identify a committed secret in the reviewed tree; a scanner cannot prove historical absence. `.env.local` is ignored and must remain unstaged. SMS IIN/password are transient; SMS session uses user-bound AES-GCM in HttpOnly cookie/TTL overflow storage. Gemini and Telegram keys are server-side. Raw auth errors, SMS state and callback codes are not logged. Root public metadata is indexable only for anonymous visitors; sitemap lists only public `/`, `/privacy`, `/terms`; authenticated content remains protected by auth/RLS, not robots.
- **RLS policy inventory:** The live project has 75 `public`/`storage` policies. Their commands, roles, `USING`/`WITH CHECK` and permissive/restrictive modes were reviewed. In particular, the `direct_messages` member policy is PERMISSIVE and `hide_deleted_message_bodies` is **RESTRICTIVE**, so the deleted-body condition is ANDed with membership rather than exposing other users' messages. Other overlapping permissive policies are admin/read alternatives or bucket-specific published-file rules. The one broad cover SELECT policy is SEC-01 above.
- **Web and abuse:** React renders untrusted text escaped; the only `dangerouslySetInnerHTML` is static theme bootstrap. External SMS/EduPage clients use origin allowlists, limits and timeouts. Upload routes have type, size and canonical-path checks; no SVG upload is accepted for avatar/cover. Next server actions retain origin checks. AI has quota/source-size/timeouts/cache; SMS challenge and Telegram notifications are bounded. Social provider rate limiting relies on Supabase/provider controls; application-specific login throttling and invite-code abuse monitoring remain operational concerns. A full script/style CSP was not added because the current inline bootstrap and runtime styles require testing nonces/hashes first.
- **Dependencies:** `npm audit --json` after the patch reports 0 known advisories across 512 dependencies. This is advisory coverage, not proof of safety. No broad or major-version dependency migration was undertaken.

## Verification and deployment gates

Isolated SQL tests in `tests/security-hardening.test.ts` verify draft cover invisibility, no direct log spoofing, anonymous RPC denial, owner-bound logging, and bounded subtasks. Auth/callback/profile tests and repository test suite cover adjacent behavior. Apply `supabase/migrations/202610020002_security_hardening.sql` **manually after existing migrations**, then verify a published cover still loads, a draft cover does not, activity logging still works, and personal tasks save normally in the real project. Re-run Supabase security/performance advisors. Enable Apple only after owner config in `docs/apple-auth-setup.md`; no live provider sign-in was performed during this audit.
